## Idea

Redesign `mcp-server/src/config.ts`'s workspace resolution so that **one** MCP server registration in Claude Desktop/Code's config can dynamically serve whichever VS Code workspace/folder is relevant to the current session, instead of pinning a workspace path at server-startup config (today: a positional CLI arg or `BOOKMARKS_MCP_WORKSPACE` env var, fixed per `mcpServers` entry — confirmed by reading `mcp-server/src/config.ts` and `mcp-server/src/index.ts` on `.worktrees/issue-52-mcp-server`, and by the original acceptance criteria in `glitchwerks/vscode-bookmarks-plus#52`: "Workspace path is supplied via MCP server config/args — no auto-discovery... one workspace per server config").

## Requirements

1. Must not require a separate MCP server registration entry per VS Code workspace (the "one server" constraint the user pushed back with).
2. Must resolve to a directory that actually contains (or lets the tools locate) `.vscode/bookmarks.json` for the workspace currently relevant to the session — not just any filesystem path the client happens to expose.
3. Must work with the clients this server actually targets — Claude Code CLI and Claude Desktop, per issue #52's title/body and `mcp-server/package.json`'s description ("exposing Bookmarks Plus's workspace bookmarks to Claude Desktop / Claude Code") — without silently breaking on either.
4. Should preserve an escape hatch equivalent to today's explicit/static config path, for deployments where dynamic resolution isn't available or reliable.
5. Should not force a breaking change onto `Config`'s downstream consumers (`mirrorPath`, `verifyDelayMs`) beyond what's needed to source `workspacePath` differently.

## Search axes used

- **Direct synonyms** — "MCP roots", "roots capability", "roots/list", "notifications/roots/list_changed"
- **Problem-shape synonyms** — "dynamic workspace resolution for MCP server", "multi-project MCP server", "current working directory MCP subprocess", "MCP server no static path"
- **Adjacent domains** — other IDE-extension + companion-process pairs solving "which project is active" (the MCP reference filesystem server has the identical shape: directory-scoped tools, one process, client tells it which directories are in scope)
- **Vendor-specific phrasing** — Claude Code docs terms: `CLAUDE_PROJECT_DIR`, "additional working directories", `--add-dir`/`/add-dir`, `additionalDirectories`
- **Negative axes** — NOT VS Code's own native MCP client (`.vscode/mcp.json` with `${workspaceFolder}` substitution) — that's a different client than the one in scope, which is Claude Desktop/Code consuming this server per issue #52. NOT remote/HTTP MCP multi-tenant session routing — this server is a local stdio process, single user, single OS session.

## Shortlist (ranked by expected value)

### 1. `modelcontextprotocol/servers` — reference filesystem MCP server's CLI-args + Roots hybrid

- **URL:** https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/index.ts (blob `234605bb137ebef5a9fc4a7b514b189bad900098`), `.../src/filesystem/roots-utils.ts` (blob `5e26bb246b5305bad3e12759baf8042f0d30b322`), `.../src/filesystem/README.md` (blob `5a7ffe791d2988146286e72870d0d2a3f4f8cff0`) — all on `main`, fetched 2026-08-09. These are content blob SHAs off a moving branch, not commit SHAs; re-fetch to confirm if `main` has moved.
- **Relevance:** addresses requirements 1 and 4 directly — directories can come from CLI args (static, today's mechanism) or from MCP Roots (dynamic, "the recommended method" per the README), and Roots notified by the client **completely replace** the CLI-supplied directories when present. Does not itself address requirement 3 (Claude-Desktop-specific verification) — it's written client-agnostically against the spec, not validated against Claude Desktop specifically in its own docs.
- **Maturity:** part of the officially maintained `modelcontextprotocol/servers` reference-servers repo, MIT licensed, actively referenced from Claude Code's own MCP docs as the pointer for "MCP server guide" material.
- **Worth borrowing:** the lifecycle and failure-handling shape, read directly from `index.ts` and `roots-utils.ts`:
  - Roots are requested inside the server's `oninitialized` callback (`server.server.oninitialized = async () => { const clientCapabilities = server.server.getClientCapabilities(); if (clientCapabilities?.roots) { try { const response = await server.server.listRoots(); ... } catch (error) { console.error("Failed to request roots from client:", ...); } } else { ... } }`) — i.e. `listRoots()` is only issued once initialization has completed, not from a top-level `createServer()`/startup path.
  - `RootsListChangedNotificationSchema` is registered as a notification handler that re-calls `listRoots()` and replaces the server's working directory set on every change.
  - If `listRoots()` throws or the client lacks the `roots` capability, the server falls back to CLI-supplied directories if any exist, and only throws a hard "server cannot operate" error if neither source produced anything — the failure mode is legible rather than a silent no-op or an unhandled hang. (Issue #3315 below is exactly the failure this pattern avoids: a client advertising `roots` but not answering `roots/list`, hanging the caller for 5+ seconds.)
  - `roots-utils.ts`'s `getValidRootDirectories()` validates that each returned root URI resolves (via `fs.realpath`) to a real, existing directory before accepting it.
- **What to avoid:** the validation in `getValidRootDirectories()` only confirms a root **exists and is a directory** — it has no concept of "is this directory usable by my tools." For this project, a root is only useful if it (or a resolvable path under it) contains `.vscode/bookmarks.json`; a bare git worktree or an unrelated open folder would pass the filesystem server's validation but fail this project's actual need. This mismatch was observed firsthand while researching this repo: the `Config`/`index.ts` files under audit here live at `.worktrees/issue-52-mcp-server/mcp-server/…` — a real, existing directory that Claude Code's roots (launch dir + `--add-dir` set) could plausibly report, and that is *not* a bookmarks-enabled workspace. The reference server's "any valid directory is a valid root" assumption does not transfer to this project without an added presence check that has no analog in the reference implementation.
- **Lift effort:** adapt-pattern — the request/notification-handler wiring is directly portable; the "is this root usable" predicate is new code specific to this project.

### 2. Claude Code's own documented roots + `CLAUDE_PROJECT_DIR` client behavior

- **URL:** https://code.claude.com/docs/en/mcp § "Option 3: Add a local stdio server" (fetched 2026-08-09); `https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md` v2.1.203 entry (fetched 2026-08-09); `modelcontextprotocol/typescript-sdk` tag `1.30.0`, `src/server/index.ts` (blob `cd75e5954a181a57d1a9d7c1967802eb561a8435`) and `src/types.ts` (fetched 2026-08-09) — this is the exact SDK version already pinned in `mcp-server/package.json` (`^1.30.0`), and it is also the current `latest` on the npm registry as of this research, so no SDK upgrade is needed to use it.
- **Relevance:** addresses requirement 1 and, for Claude Code specifically, requirement 3. Partially addresses requirement 2 (same "root ≠ guaranteed bookmarks workspace" caveat as candidate #1). Does not address requirement 3 for Claude Desktop — unverified, see "No prior art found" below.
- **Maturity:** the SDK's `Server` class (the low-level class `McpServer` wraps; this project uses `McpServer`) already exposes `async listRoots(params?, options?)` calling `roots/list`, and `assertCapabilityForMethod` already gates it on `this._clientCapabilities?.roots`, confirmed by reading the actual `1.30.0` tag source. `RootSchema`, `ListRootsRequestSchema`, `ListRootsResultSchema`, and `RootsListChangedNotificationSchema` are all present in `src/types.ts` at that tag. However, **`McpServer` (the high-level API this project's `index.ts` uses) has no roots-specific convenience method** — confirmed by fetching `src/server/mcp.ts` at the same tag and finding no mention of roots; a caller must reach through the `server.server` property to the low-level `Server` instance to call `listRoots()` or register the `RootsListChangedNotificationSchema` handler.

  Client-side, Claude Code's support for roots has a documented maturity history, not a clean "always worked" story:
  - `anthropics/claude-code#3315` ("MCP roots capability advertised but roots/list method not implemented"), opened 2025-07-11 against Claude Code 1.0.48/MCP protocol 2025-06-18, reported that Claude Code advertised `capabilities.roots` at initialize but never answered `roots/list`, causing a 5+ second timeout on the calling server. Closed as stale/`not_planned` 2026-02-08.
  - `anthropics/claude-code#26663` ("`/add-dir` does not send `notifications/roots/list_changed` to MCP servers"), opened 2026-02-18 against Claude Code v2.1.39, reported that mid-session `/add-dir` updated Claude Code's internal state but never notified connected MCP servers, so root-validating servers silently rejected newly added directories. Closed as stale 2026-03-19.
  - The current `CHANGELOG.md` records, under v2.1.203: "Added the session's additional working directories to MCP `roots/list`, with `notifications/roots/list_changed` sent when the set changes" — i.e. both gaps above are now closed in the currently documented behavior. The docs page (fetched today) states this in present tense as working behavior: "Claude Code answers `roots/list` with the session's launch directory plus every additional working directory you've granted with `--add-dir`, `/add-dir`, or the `additionalDirectories` setting... Before v2.1.203, `roots/list` returned only the launch directory and Claude Code didn't send `notifications/roots/list_changed`."
- **Worth borrowing:** the vendor's own explicit, dated recommendation for exactly this problem shape, quoted directly from the docs: "`CLAUDE_PROJECT_DIR` is the stable project root and doesn't change when you add or remove working directories mid-session. A server that limits its own filesystem access to a set of allowed directories should implement the MCP `roots/list` request instead." This is a direct statement of which of the two Claude-Code-specific mechanisms Anthropic itself points servers toward for scoping filesystem access.
- **What to avoid:** neither `CLAUDE_PROJECT_DIR` nor Claude Code's roots answer describe "the VS Code workspace with the bookmarks extension open" — they describe **Claude Code's own session directory set** (the directory `claude` was launched from, plus anything added via `--add-dir`). The two coincide in the common case (a developer runs `claude` from the same repo root that VS Code has open) but desync whenever they don't — e.g. a git worktree checkout, a monorepo subdirectory, or a session launched from `$HOME`. Also relevant: `anthropics/claude-code#75266` (title: "Claude Code desktop app launches MCP servers with cwd set to `$HOME` instead of the session's project directory") surfaced in search results as an open, apparently-unresolved report — inherited process `cwd` should not be treated as a reliable substitute for the explicit `CLAUDE_PROJECT_DIR` env var or roots.
- **Lift effort:** adapt-pattern — SDK primitives are already available at the pinned version; the resolution/fallback ordering against the current CLI-arg/env-var mechanism is new code.

### 3. `cline/cline` discussion #2635 — tool-argument (`workspace_path`) pattern, as a data point on the tradeoff, not as adoptable code

- **URL:** https://github.com/cline/cline/discussions/2635 (fetched 2026-08-09)
- **Relevance:** addresses requirements 1 and 3 (client-agnostic — works against any MCP client regardless of roots support) at the cost of requirement 5 (it's a tool-schema change on every affected tool, not a `resolveConfig` change).
- **Maturity:** this is a still-open discussion thread on the Cline VS Code extension (a Cline/Roo-Code-family MCP client), not a shipped Cline feature — as of the thread's most recent visible comments, Cline had not implemented MCP roots support, and a participant characterized the project as "totally unaware" that passing workspace path as a tool argument was even an option worth documenting.
- **Worth borrowing:** only the tradeoff data point, reported directly by a practitioner who tried it: making the workspace directory an explicit argument on every tool call "works flawlessly" but "adds burden to every tool call." No code to port — this is confirmation of a pattern the model already tends toward per the user's own framing (Claude usually knows the current working directory/open folder from its own session context), not a library or reference implementation.
- **What to avoid:** the pattern has no protocol-level guarantee that the calling model supplies the argument correctly or at all — reliability depends on tool description quality and the calling model's judgment on every single call, not on the client/server handshake enforcing it once at connect time the way roots does.
- **Lift effort:** study-only.

## No prior art found

- **Confirmation that Claude Desktop (the standalone chat app, not the "Code tab" that wraps Claude Code sessions) implements the MCP client-side `roots` capability.** Searched modelcontextprotocol.io's roots spec page, `code.claude.com/docs/en/mcp` (which is Claude-Code-CLI-scoped and doesn't describe Desktop's own MCP client separately), and `claude.com/docs/third-party/claude-desktop/local-access`. That last page describes a *different* feature — Cowork's `allowedWorkspaceFolders` sandbox-attachment allowlist, which governs which folders a user can attach to a Cowork sandbox VM session, not the MCP `roots/list`/`notifications/roots/list_changed` protocol primitive. General web search returned only synthesized/SEO summaries with no primary citation for Desktop's roots support one way or the other. Implementer should verify empirically — connect the server to a real Claude Desktop session and log `server.server.getClientCapabilities()` — rather than assume support either way before committing to a roots-primary design.
- **A discriminator for "which returned root is the bookmarks workspace"** when `roots/list` returns zero, one, or several entries and not all of them are guaranteed to contain `.vscode/bookmarks.json`. Neither the MCP spec nor the reference filesystem server addresses this, because it's specific to this project's requirement that a usable root also carry the bookmarks mirror file — the filesystem server's tools operate identically on any valid directory, so it has no equivalent problem. This is downstream design work for the implementer, not something with external prior art to draw from.

## Recommended handoff

- `project-planner` — design against the CLI-args + Roots hybrid lifecycle from candidate #1 (`modelcontextprotocol/servers` filesystem reference server), informed by Claude Code's documented `CLAUDE_PROJECT_DIR`/roots behavior in candidate #2. Open decisions for the planner: the fallback ordering between the roots-supplied set, `CLAUDE_PROJECT_DIR`, and today's explicit CLI-arg/env-var mechanism (requirement 4); the bookmarks-file-presence discriminator when multiple/ambiguous roots are returned (the "no prior art" gap above); and whether a per-call `workspacePath` tool argument (candidate #3's pattern) is worth adding as a last-resort override for the Claude-Desktop-unverified case.
- `user` — resolve the Claude Desktop gap before the planner locks in a design: confirm whether the target client set for this MCP server is "Claude Code only" or "Claude Code + Claude Desktop." If Desktop must be supported and its roots support turns out to be absent or unreliable, a roots-primary design alone won't satisfy requirement 3, and the fallback layer (CLI arg, or a tool-argument override) becomes load-bearing rather than a defensive extra.
